## Part A — Kill the next/font CJK preload flood

**Problem.** `apps/web/src/lib/fonts.ts` declares `Noto_Serif_SC`, `Noto_Serif_JP`, and `Zen_Kaku_Gothic_New` via `next/font/google`. Google Fonts ships each CJK family as 80–110 `unicode-range`-chunked woff2 files (one per range like `U+4E00-9FFF`, `U+30A0-30FF`, etc.). `next/font` defaults `preload: true`, so every chunk gets a `<link rel="preload" as="font">` in `<head>` plus the `Link:` response header. Empirical: 123 font preloads on `/en`, 68 on `/en/posts`, 55 in `Link`. Total font payload 1.6–2.2 MB per page, all racing for slow-4G bandwidth on cold load.

This starves the JS bundle of bandwidth, delays hydration, delays the motion entrance animation, and the late font-swap retriggers LCP candidate selection. Single biggest win.

### A1. Disable preload on CJK next/font declarations

File: `apps/web/src/lib/fonts.ts`

Add `preload: false` to all three CJK families. Keep `Instrument_Sans` preloaded (it's latin-only, one ~30 KB file, used by every locale's `--app-font-sans` slot).

```ts
const sansFontJa = Zen_Kaku_Gothic_New({
  subsets: ['latin'],
  weight: ['400', '500'],
  variable: '--app-font-sans-ja',
  display: 'swap',
  preload: false,        // ← add
  fallback: ['Zen Kaku Gothic New'],
})

const serifFontSc = Noto_Serif_SC({
  subsets: ['latin'],
  weight: ['400'],
  variable: '--app-font-serif-sc',
  display: 'swap',
  preload: false,        // ← add
  fallback: ['Noto Serif SC'],
})

const serifFontJa = Noto_Serif_JP({
  subsets: ['latin'],
  weight: ['400'],
  variable: '--app-font-serif-ja',
  display: 'swap',
  preload: false,        // ← add
  fallback: ['Noto Serif JP'],
})
```

What this does:
- Stops emitting `<link rel="preload">` for all unicode-range chunks. The `@font-face` rules are still inserted (next/font writes them into a generated CSS file), so the browser still loads woff2 files **on demand** — only the ranges that actually contain rendered glyphs.
- For `en` and `zh-TW` (whose serif stack falls back to Georgia/Songti before reaching the next/font variable in practice), most chunks are never requested.
- For `ja`, the page only fetches the kanji ranges used by visible characters, not all 80+ files.

Risk: short-term FOUT on first-load until the right range arrives. Mitigated by `display: 'swap'` already set, plus `adjustFontFallback` (next/font default `true`) which writes size-matched fallback metrics so swap doesn't visibly resize text. Confirm there's no `adjustFontFallback: false` anywhere — there isn't.

Expected: 123 preloads → ≤2 (just Instrument Sans 400 + 500). Cold-load font transfer drops from ~2 MB to <100 KB.

### A2. Prune `--app-font-serif-sc` from non-CJK locale stacks

File: `apps/web/src/lib/font-locale.ts`

The `en` serif stack currently lists `var(--app-font-serif-sc)` first. Even with A1 (preload off), the CSS variable is still resolved when a serif element renders in English text, triggering on-demand chunk fetches for latin ranges. Drop the variable for non-CJK locales:

```ts
en: [
  'Georgia',
  "'Times New Roman'",
  'serif',
].join(', '),

// zh-TW: keep var(--app-font-serif-sc) — TC uses SC serif fallback by design
```

Leave `zh`, `zh-TW`, `ja` as-is (they actually need the CJK glyphs).

Risk: visible style shift on `<blockquote>`, hitokoto, etc. in English. Inspect `/en` + `/en/posts/*` in browser before/after; if Georgia diverges too far, swap to a self-hosted single-file latin serif via `/fonts/`.

### A3. Verify

After A1 + A2, rebuild and re-count:

## Part B — opacity 0.001 hack on LCP-eligible motion entrances

**Problem.** Hero `m.h1` on `/en` and similar entrance-animated headings start at `opacity: 0` and animate to `1` via framer-motion. Chrome's LCP algorithm only considers an element painted when computed `opacity > 0`, so the LCP candidate isn't picked until hydration completes and motion fires the first frame. With JS + fonts contending on slow-4G this pushes LCP to 15–29s even when the breakdown audit shows the underlying TTFB + render delay is ~600ms.

User-confirmed approach: start `opacity` at `0.001`. Visually indistinguishable from 0; LCP algorithm treats it as painted. Animation still runs to 1.

### B1. Patch Hero's `riseProps` / `fadeProps`

File: `apps/web/src/app/[locale]/(home)/components/Hero.tsx`

```ts
const riseProps = (delay: number) => ({
  initial: { opacity: 0.001, y: 12 },
  animate: { opacity: 1, y: 0 },
  transition: { duration: 0.6, ease: EASING, delay },
})

const fadeProps = (delay: number) => ({
  initial: { opacity: 0.001 },
  animate: { opacity: 1 },
  transition: { duration: 1, ease: EASING, delay },
})
```

The `y: 12` translation on `riseProps` is fine — translate alone doesn't gate LCP, only opacity does.

### B2. Same pattern in `SecondScreen.tsx`

File: `apps/web/src/app/[locale]/(home)/components/SecondScreen.tsx`

Uses the same `riseProps` style locally. Either import the patched helpers from `Hero.tsx` or apply the same 0.001 swap inline. (Prefer extracting to a shared module — see B4.)

### B3. Audit other top-level pages for raw `m.*` entrances

`BottomToUpSoftSpringTransitionView` (`apps/web/src/components/ui/transition/factor.tsx:76`) already implements the optimization differently: when `lcpOptimization` prop is true and hydration hasn't ended, it sets `initial = to` and removes `animate`, so the element renders in its final state and the animation never plays on first load. That's stronger than the 0.001 hack — it skips the animation entirely on cold load — but it requires using this wrapper instead of raw `m.*`.

`/en/posts`, `/en/thinking`, and post detail already pass `lcpOptimization` to this wrapper. So if measurements still show motion-gated LCP on those pages after A, the issue isn't here. Verify post-A.

Grep for remaining raw `m.h1 / m.h2 / m.section` etc. above the fold on the routes we audit and convert them to use either:
- The 0.001 hack (preserves animation on cold load), or
- `BottomToUpSoftSpringTransitionView` with `lcpOptimization` (skips animation on cold load).

Pick per-design intent. Hero wants the entrance animation visible → 0.001. List headers don't → use the wrapper.

```bash
# audit
rg -n "^\s*<m\.(h1|h2|h3|section|article|main|div)" apps/web/src/app apps/web/src/components/modules
```

### B4. Extract a shared helper

`apps/web/src/components/ui/motion/lcp-safe-entrance.ts` (new):

```ts
export const LCP_SAFE_OPACITY = 0.001

export const riseInLcpSafe = (delay = 0, opts: { y?: number; duration?: number } = {}) => ({
  initial: { opacity: LCP_SAFE_OPACITY, y: opts.y ?? 12 },
  animate: { opacity: 1, y: 0 },
  transition: { duration: opts.duration ?? 0.6, ease: [0.22, 1, 0.36, 1] as const, delay },
})

export const fadeInLcpSafe = (delay = 0, opts: { duration?: number } = {}) => ({
  initial: { opacity: LCP_SAFE_OPACITY },
  animate: { opacity: 1 },
  transition: { duration: opts.duration ?? 1, ease: [0.22, 1, 0.36, 1] as const, delay },
})
```

Then replace local `riseProps` / `fadeProps` in Hero.tsx and SecondScreen.tsx with these. Future ad-hoc entrances should import these instead of redefining.

## Part C — CLS fixes (no editor split)

Three concrete sources from the baseline reports. Estimated impact per shift is in the `layout-shifts` audit JSON.

### C1. `/en/thinking` — `<main className="mt-9">` shift, CLS = 0.669 (catastrophic)

File: `apps/web/src/app/[locale]/thinking/page.tsx:40`

The `<main>` reports score 0.6689 — the entire main column moves after first paint. Likely cause: `List` (line 50–101) renders nothing while `useInfiniteQuery` is loading (the `if (isLoading) <Loading … />` on line 73 returns the JSX expression but doesn't actually return it from the function — note the missing `return` — so `<List>` renders an empty `<ul>` until data arrives). When data lands, the populated `<ul>` injects a tall block and everything below jumps.

Two-part fix:

1. **Fix the dropped `return`** on line 73:
   ```diff
   - if (isLoading) <Loading useDefaultLoadingText />
   + if (isLoading) return <Loading useDefaultLoadingText />
   ```
   This alone doesn't help CLS (loading skeleton → list is still a shift), it's just a latent bug. But it's right next door, so do it.

2. **Reserve vertical space** so the populated list doesn't push the rest of the page. Either:
   - Render server-side initial data (preferable — convert this page or `<List>` to async server component with prefetched first page, hydrate React Query with the server-fetched data), or
   - Wrap `<List>` in a min-height container sized to roughly `FETCH_SIZE × item-height`. Cheap but visually empty until data lands.

Prefer option 1 (SSR prefetch). Server-fetch `apiClient.shorthand.getList({ size: FETCH_SIZE })` in `page.tsx`, hand to `dehydrate(queryClient)` and `<HydrationBoundary>` so the client query rehydrates without a loading flash. There's an existing pattern in `apps/web/src/queries/` to follow.

### C2. `/en/posts` — list reflow, CLS = 0.044 local / 0.113 prod

File: `apps/web/src/app/[locale]/posts/page.tsx:130`

The `<div data-fetch-at={fetchedAt}>` wrapper is around server-rendered `listItems.map(...)`. The list is SSR'd so it shouldn't shift. The likely culprit is the `BottomToUpSoftSpringTransitionView` wrappers (line 132) — they pass `lcpOptimization` so SSR renders in-place, but during hydration the motion ref-resolves and recomputes layout briefly. Prod shows higher (0.113) than local, suggesting it's image-aspect-ratio or font-swap related.

Audit the post list item:

```bash
rg -n "PostListItem|PostFeaturedCard" apps/web/src/components/modules/post --files
```

Verify each `<Image>` inside has explicit `width` + `height` (or `fill` + sized parent). Verify tag chips, cover thumbnails, hover decorations don't add layout after hydration. The prod jump from 0.044 → 0.113 hints at images without intrinsic dimensions.

Fix per finding. No spec changes yet — needs the source files first.

### C3. `/en/posts/[c]/[s]` — comment-gutter shifts, CLS = 0.024 local / 0.117 prod

File: `apps/web/src/components/modules/comment/LexicalCommentWrapper.tsx:152-167`

The wrapper `<div className="group/comment-block relative lg:pr-8" data-comment-gutter-host="">` is SSR'd with stable padding, so the wrapper itself doesn't shift. The five repeated CLS rows in the report (`score=0.0073, 0.0043, 0.0040, 0.0033, 0.0029`) are five separate divs with the same className — meaning the gutter is mounting comment threads / anchors after hydration and each insertion bumps surrounding content.

Inspect `CommentBlockGutter` and `CommentAnchorHighlight`. They're rendered inside `RichContentElementProvider` (line 159) which probably measures the rich content container and positions gutter elements absolutely. If gutter elements end up in normal flow (e.g., a fallback before refs resolve), each frame of positioning is a shift.

Fix path:
- Ensure all gutter / anchor elements use `position: absolute` from first render, regardless of ref availability.
- If gutter needs to push content sideways, reserve that width statically (already done with `lg:pr-8`).
- If existing comments are SSR'd into the gutter, render them with `visibility: hidden` until measured, not `display: none → block` swap.

Prod 5× higher than local suggests this scales with real comment counts. Worth investigating against a post that actually has comments rather than the test article.

## Sequencing

1. **Land A first** — single PR, three files (`fonts.ts`, `font-locale.ts`, plus rebuild). Easiest to validate (count preloads + rerun lighthouse). Expected to swing LCP the most.
2. **Then B** — Hero 0.001 + shared helper + audit. Small surface, targeted at home LCP that A alone won't fully fix (motion-gated).
3. **Then C1** (thinking SSR prefetch) — biggest CLS win, isolated change.
4. **C2 + C3** in parallel — depend on inspecting list/comment internals, treat as follow-ups.

Re-run `perf/baseline/run-lighthouse.sh <date>` after each PR to track regression. Three measured runs (not one) once the numbers compress under 5s — sub-second runs need lower variance.

## Out of scope (explicit)

- Splitting `@haklex/rich-static-renderer` or any editor JS — SSR first-paint dependency.
- Switching off Motion / framer-motion globally.
- Migrating away from next/font for `Instrument_Sans`.
- Locale-routing fix for `next start` rewrite leak — baseline tooling uses `/en/*` and that's fine for regression detection.
